## Build System

QNode uses CMake with Ninja as the default generator. The build process is cross-platform supporting Windows (MSVC/MinGW), macOS, and Linux.

### Building the Project

```bash
# Configure CMake (from root directory)
cmake -B build -S . -G Ninja

# Build all targets
cmake --build build

# Clean build
rm -rf build && cmake -B build -S . -G Ninja
```

### Build Targets

The project builds the following executables in `build/bin/`:
- `qnode` - Main QNode runtime executable
- `qjs` - Alias for qnode (same executable)
- `qjsc` - QuickJS compiler (used during build process)

### CMake Configuration Options

- `CONFIG_BIGNUM=OFF` - Enable/disable bignum support
- `USE_WORKER=OFF` - Enable/disable Worker API
- `CONFIG_VERSION=ON` - Enable version string
- `ENABLE_DEBUG=OFF` - Enable debug output
- `ENABLE_LTO=OFF` - Enable link-time optimization

Example: `cmake -B build -S . -G Ninja -DENABLE_DEBUG=ON -DENABLE_LTO=ON`

## Architecture

QNode is a Node.js-like runtime built on top of QuickJS, following a modular architecture:

### Core Libraries

The project is organized into three static libraries:

1. **quickjs_deps** (`src/deps/`) - Basic dependencies
   - `cutils.c/h` - C utility functions
   - `dtoa.c/h` - Double to ASCII conversion
   - `libregexp.c/h` - Regular expression engine
   - `libunicode.c/h` - Unicode support

2. **quickjs_core** (`src/core/`) - QuickJS core engine
   - `quickjs.c` - Main JavaScript engine implementation
   - `quickjs.h` - Public API headers

3. **quickjs_libc** (`src/lib/`) - Standard library bindings
   - `quickjs-libc.c` - C library bindings for JS runtime
   - Provides `std` and `os` modules for JavaScript

### Runtime Architecture

The main runtime (`src/qnode.c`) implements:

- **Context Management** - `JS_NewCustomContext()` creates JS contexts with std/os modules
- **Evaluation** - Supports both script and module evaluation modes
- **REPL Integration** - Includes interactive REPL built from `src/repl.js`
- **Memory Management** - Optional memory tracing and limiting
- **Worker Support** - Configurable Worker API integration

### Build Process Flow

The build has a custom workflow:

1. Build `qjsc.exe` compiler first
2. Use `qjsc` to compile `src/repl.js` into `src/repl.c` (bytecode)
3. Link `repl.c` into final `qnode`/`qjs` executables

This compilation step ensures the REPL is embedded as bytecode rather than interpreted at runtime.

### Platform-Specific Considerations

- **Windows**: Static linking by default to avoid DLL dependencies. Uses `ws2_32` for sockets.
- **Linux/macOS**: Links against `pthread`, `dl`, and `m` (math) libraries
- **MSVC**: Requires special compatibility headers (`include/msvc_compat.h`) and UTF-8 source handling

### Source File Organization

- `src/qnode.c` - Main runtime entry point
- `src/qjsc.c` - QuickJS compiler for compiling JS to bytecode
- `src/repl.js` - Read-Eval-Print Loop implementation (compiled to C)
- `include/quickjs.h` - Main QuickJS public API
- `include/msvc_compat.h` - MSVC compatibility layer
- `include/qnode_config.h` - Configuration header generated by CMake

### Running QNode

```bash
# Interactive mode
./build/bin/qnode

# Run a file
./build/bin/qnode script.js

# Evaluate expression
./build/bin/qnode -e "console.log('Hello')"

# Module mode
./build/bin/qnode -m module.mjs

# With memory limit (e.g., 100MB)
./build/bin/qnode --memory-limit 100M script.js
```
